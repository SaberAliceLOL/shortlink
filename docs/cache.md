# 短链服务的缓存层：三种异常、两种击穿策略与实测数据

> 本文对应 Week 3-4。所有数字都是本机实测（16 核 / 7.5G WSL2，
> MySQL 8.4 + Redis 7.4 各自跑在 Docker 里，**不是**云服务器的数据）。
> 复现命令在文末。
>
> 写这篇的目的不是罗列八股，而是回答一个问题：
> **这个场景下，哪一种"标准做法"其实没用？**

---

## 0. 一句话结论

| 异常 | 常规答案 | 本项目的选择 | 为什么 |
|---|---|---|---|
| 穿透 | 布隆过滤器 | **水位守卫**（布隆作为对比实现保留） | 短码 = Base62(自增 ID)，键空间单调，"ID 超过水位"就是零内存的确定性判断 |
| 击穿 | SETNX 互斥锁 | **逻辑过期**（互斥锁保留可切换） | 短链不可变，旧值不会错只会旧；实测过期瞬间 P99 19ms vs 83ms |
| 雪崩 | TTL + 随机抖动 | 同上，且**降级是主要防线** | 抖动只挡"集体过期"，挡不住"Redis 整体挂掉"——那要靠熔断 |

一句话：**三种异常里，只有"击穿"有唯一正确答案，而且答案取决于数据是否可变。**

## 1. 先定清楚：缓存是加速器，不是数据源

整个模块的所有设计都从这个前提出发：

```
Redis 故障  ≠  服务故障
缓存未命中  ≠  请求失败
```

具体到代码，每一条 Redis 调用都包在 `try/except` 里，失败就 `breaker.trip()` 并退化为直接查库。
唯一"宁可失败也不能瞎返回"的地方是**前置过滤器**——它出错必须放行，因为误杀真实链接（用户看到 404）
比多查一次库严重一个数量级。

这个取舍有个代价，必须承认：Redis 挂掉时，DB 承受的是**全量**读压力。
所以下面第 6 节的熔断不是为了"让请求更快失败"，而是为了**把故障成本从"每请求一次超时"
摊薄成"每个冷却期一次探测"**——没有熔断时，一个挂掉的 Redis 会让每个请求都等满
socket timeout（本篇配的是 0.5s），服务不是降级，而是每次多 500ms 的降级。

## 2. 穿透（penetration）：用错了工具

### 2.1 问题的真实形态

穿透是"查询一个库里根本不存在的短码"。在短链场景里，它有两个截然不同的来源：

| 来源 | 特征 | 谁挡得住 |
|---|---|---|
| 攻击者乱猜 | ID **远超**已分配最大值 | 前置过滤（水位/布隆）都能挡 |
| 号段内空洞 | ID 在已分配号段内，但那个号从没发出去 | **只有负缓存能挡**，过滤器无能为力 |

第二类最容易被忽略：号段式发号器的 `max_id` 是"已分配到哪"，不是"发到哪"。
一次取 1000 个号，实际可能只发出去 3 个，剩下 997 个是"看起来合法但不存在"的短码。
**过滤器对它们一律放行**——因为 `ID <= 水位` 无法否定存在性。

### 2.2 为什么不用布隆过滤器

布隆过滤器是对的通用答案，但在**这个**场景里它不是最优解，原因不是性能，是正确性风险：

1. **必须预热**。上线时库里已有的短码要全量灌进位图，漏了就变成假阴性
   （真实链接被判不存在）——这是事故，不是性能问题。
2. **假阳性是概率性的**，且随数据量增长。1 亿条要 ~120 MiB 位图 + 1% 误判。
3. **Redis 清空就得重建**，而重建又回到第 1 条。
4. 它唯一的核心优势——"任意键空间也能判"——在这里等于放弃了手里最有价值的信息。

水位守卫把这些全部消掉：

```
ID > 已分配 max_id  ⇒  一定不存在     （发号器严格递增，永不回头）
ID ≤ 已分配 max_id  ⇒  不保证存在     （号段已分配但号没发完）
```

O(1) 内存（两个整数）、零假阴性、从 DB 读一行就能恢复。

代码保留了两套实现（`app/services/prefilter.py`），配置里 `PREFILTER_STRATEGY=watermark|bloom|none` 可切，
压测脚本会用同一套负载分别测——**面试时可以说"两种我都实现过，选水位是因为 xxx"**，
这比"我用了布隆过滤器"有信息量得多。

### 2.3 水位的安全边界（这里最容易写错）

水位是**本地缓存**的，会落后于 DB 里的真实值。落后的窗口里，刚生成的短码会被判成
"不存在"——这是唯一危险的方向。

两道保险：

1. **margin**：判定阈值 = `max_id + margin_steps × step`。
   margin=10、step=1000 → 每次号段分配能覆盖 1 万个新号，即每秒 1 万个新链接以内绝对安全。
2. **进程内抬升**：`create()` 发号后立刻 `note_issued_id()`，自己刚发的号绝不会被自己拒掉。
   margin 只用来跨进程兜底。

**刷新失败时必须整体放行。** 这一点是写测试时发现的：最初实现里刷新失败只记日志、
继续用旧水位判定。这在一个刷新周期内是安全的（margin 兜得住），但连续失败意味着
"我们不知道这期间又发出去多少号"，margin 不再是**有界**误差。
所以 `_healthy=False` 后 `threshold` 直接返回 -1，一律放行。
对应测试：`tests/test_prefilter.py::TestWatermark::test_db_failure_allows_everything`。

### 2.4 实测

每轮 2000 请求、100 并发，20 个不存在的短码轮转：

| 场景 | QPS | P50 | P99 | DB 回源 |
|---|---|---|---|---|
| 未来号（>水位）· 无防护 | 1331 | 63.4ms | 161ms | 2000 |
| 未来号 · 仅负缓存 | 5365 | 14.2ms | 118ms | 100 |
| 未来号 · 负缓存 + 水位过滤 | **34274** | **2.8ms** | **3.6ms** | **0** |
| 号段内空洞 · 无防护 | 1391 | 63.8ms | 157ms | 2000 |
| 号段内空洞 · 仅负缓存 | 4950 | 14.0ms | 152ms | 100 |
| 号段内空洞 · 负缓存 + 水位过滤 | 5431 | 14.0ms | 125ms | 100 |

三个可讲的点：

1. **水位过滤把 QPS 拉到 34k，因为请求根本没到 Redis**。这是"在更前面挡住"的复利：
   层数越靠前，单位收益越大。
2. **对号段内空洞，过滤器完全无效**（QPS 4950 → 5431，在噪音内）。
   这正是 2.1 里说的"两类来源、不同防线"。只测一类会得出错误结论。
3. **30k+ 的 QPS 是进程内数字**（直接调 service），不代表线上 HTTP 吞吐。
   HTTP 层见第 5 节。

### 2.5 负缓存的两个陷阱

**陷阱一：短码可预测。** 短码 = Base62(自增 ID)，下一个短码是**算得出来的**。
攻击者可以先请求一个还没生成的短码，把 404 写进负缓存；等链接真的生成后，
用户在负缓存 TTL 内访问会拿到 404。

解法：写入路径**主动覆盖**负缓存（`create()` 里 `cache.store()`），而不是等它自然过期。
对应测试：`test_shortlink_service.py::test_create_overwrites_preplanted_negative_cache`。

**陷阱二：负缓存不能太长。** 它挡的是攻击流量，但也可能挡住真实新建的链接（如果不覆盖）。
本项目的选择是 60s + 50% 抖动，并且靠写入覆盖兜底。长 TTL 省的那点 DB 查询，
换来的风险不值得。

## 3. 击穿（breakdown）：两种策略，我有实测数据

### 3.1 先把场景分清楚

"击穿"通常被描述成"热点 key 失效瞬间大量请求回源"。但这里其实有**两种失效**，
它们的结论正好相反，混在一起谈就说不清了：

| 场景 | 状态 | 关键区别 |
|---|---|---|
| **冷启动** | key 从未被写过 | 没有旧值可返回，逻辑过期退化成无保护 |
| **过期瞬间** | key 存在但已过期 | 有旧值可用，逻辑过期可以立即返回 |

这个区分是整个第 3 节的骨架。压测里两个都跑，因为它们回答的是不同问题：
"第一次访问怎么办"和"整点过期怎么办"。

### 3.2 两种实现

**互斥锁（`CACHE_STRATEGY=mutex`）**

```
miss → SETNX lock → 拿到锁的请求回源 → 其余请求短暂等待（最多 3×50ms）后复用结果
                  → 等不到就自己回源（宁可多打一次 DB，也不无限排队）
```

关键点：**等待必须有上限**。无限等锁等于把缓存故障放大成请求堆积——
这是把"击穿"修成"雪崩"的经典写法。

锁释放必须用 Lua 比对 token 再删：
```
A 拿锁 → A 卡住 → 锁自动过期 → B 拿锁 → A 醒来 DEL 掉了 B 的锁
```
直接 `DEL` 就会踩这个坑，而这在压测里极难复现、在线上偶发。

**逻辑过期（`CACHE_STRATEGY=logical_expire`）**

值里带一个逻辑过期时间戳 `expire_at_ms`；Redis 键本身 TTL 比它多活 `stale_grace`（600s）。

```
读到记录 → 逻辑未过期 → 直接返回
         → 逻辑已过期 → 立即返回旧值 + spawn 后台刷新
```

前提是**数据不可变**。短链没有编辑/删除接口，所以旧值不会"错"，只会"稍旧"。
如果哪天加了"修改目标 URL"，这个策略就必须换成互斥锁，或者引入主动失效。

### 3.3 实测：过期的两种形态

每轮 1000 请求、100 并发，全部打同一个热点短码：

| 场景 | QPS | P50 | P99 | DB 回源 | 备注 |
|---|---|---|---|---|---|
| 冷启动 · 无保护 | 4193 | 15.1ms | 120ms | 100 | 全部并发回源 |
| 冷启动 · 互斥锁 | 4620 | 13.1ms | 110ms | **1** | 锁生效 |
| 冷启动 · 逻辑过期 | 4302 | 14.2ms | 122ms | 100 | **退化**：没有旧值可返回 |
| 过期瞬间 · 无保护 | 4479 | 13.9ms | 116ms | 100 | |
| 过期瞬间 · 互斥锁 | 5357 | 13.2ms | 82ms | **1** | 其余请求等锁/复用 |
| 过期瞬间 · 逻辑过期 | **6905** | 13.5ms | **19ms** | **1** | 旧值直接返回，刷新后台做 |

结论很清楚：

- **冷启动时逻辑过期帮不上忙**，它和无保护一样会 100 次回源。这是它的固有边界，不是实现问题。
- **过期瞬间逻辑过期全面胜出**：P99 19ms vs 无保护 116ms，QPS 6905 vs 4479。
  因为 99 个请求什么都不等。
- 互斥锁在两个场景都把回源压到 1 次，但代价是请求要排队——所以 P99 是 82ms，比逻辑过期的 19ms 差。

**这组数字就是"选逻辑过期"的依据。** 面试被问"为什么不用互斥锁"时，
可以直接说"两者我都实现了，互斥锁把 P99 从 116ms 降到 82ms，逻辑过期降到 19ms，
区别在于前者仍然要等重建、后者不用等"。

### 3.4 一个必须讲的 bug：单飞写漏了

第一版逻辑过期在"过期瞬间"跑出 **2069 QPS / P99 325ms / 901 次回源**——
比无保护还差，而且回源次数是请求数的 90%。

根因有两层，压测是逐层剥开的：

**第一层：刷新任务拿到锁后没复查。**
100 个请求各 spawn 一个刷新任务；第一个刷完释放锁后，排队中的任务会**依次**再拿到锁，
各自再查一次库。锁只保证"同时只有一个"，不保证"后来者知道前面已经干完了"。

修法：拿到锁后先 `_read()` 复查，发现已经不 stale 就直接退出。
修完 901 → 1。

**第二层：单飞做晚了。**
即使复查修好，100 个请求仍然各自 spawn 了一个 task、各自打了一次 `SETNX`。
保护措施本身成了瓶颈：P99 仍在 300ms 量级。

修法：在 spawn **之前**先查进程内集合 `_inflight`，零成本挡掉 99 个。
Redis 锁仍然保留——它管的是跨进程的单飞。

修完：**6905 QPS / P99 19ms / 1 次回源**。

**这个故事的价值**：这两个问题都是"能跑、能过测试、但性能不对"的类型，
只有压测能打出来。对应回归测试：
`test_cache.py::TestBreakdownLogicalExpire::test_refresh_rechecks_after_acquiring_lock`——
50 个并发过期命中，断言回源恰好 1 次。

### 3.5 一个压测本身的坑（也要讲）

第一版压测的"过期瞬间"场景构造错了：我用**一天前**的时钟写入缓存，
让记录一落地就是"逻辑过期"。但后台刷新写回的新记录 `expire_at = 一天前 + ttl` **依然是过期的**，
于是每个刷新任务复查后都判定"还要再刷"——回源数照样飙到 901。

正确的构造是回溯 `ttl + 100` 秒：足够越过过期线，但刷新写回的新记录是**有效**的。
脚本里为此加了一条断言，确认场景真的处于"存在但过期"状态才开跑。

**教训：压测的构造方式本身会骗人。** 如果一个优化看起来"完全没效果"，
先怀疑测法，再怀疑实现——但反过来，如果实现里真有 bug，正确构造才能暴露它。
这次两个都撞上了（先修实现、再修构造）。

## 4. 雪崩（avalanche）：抖动只是第一层

### 4.1 TTL 抖动

```
真实 TTL = ttl × (1 ± ratio)      # 默认 300s × (1±20%) → 240~360s
```

为什么抖动加在**写入侧**而不是读取侧：加在写入侧等于把过期点沿时间轴均匀铺开；
加在读取侧（"过期后随机重试"）只是把雪崩推迟到下一轮。

对应测试：`test_ttl_has_jitter`（20 个键的 TTL 不能全相同）、
`test_jitter_stays_near_base_ttl`（必须落在 240~360 区间内，不能飘出去）。

### 4.2 抖动挡不住的两种情况

抖动解决的是"**同一批写入的键在同一个时刻集体过期**"。它挡不住：

1. **Redis 整体不可用** —— 这不是雪崩，是依赖故障。靠熔断 + 降级（第 1 节）。
2. **重启后缓存全空** —— 所有请求同时 miss。这时负缓存和前置过滤仍在工作，
   但真实短码只能回源。**这才是"多级缓存"真正有意义的场景**：
   本地 LRU 在 Redis 重启时能挡住大部分读。
   本项目 Week 5 会加本地 LRU 并测它对"Redis 重启"这个场景的贡献。

### 4.3 为什么现在不做多级缓存

因为现在做就说不清收益。Week 5 会用同一套压测脚本先量"Redis 挂掉"时的 QPS 基线，
再决定本地 LRU 值不值得加——**没有数据支撑的架构就是过度设计**。
这也是路线图里"每次只改一个变量"的意思。

## 5. Connection pool 与 uvloop

### 5.1 连接池

配置从 `app/core/config.py` 走环境变量，池大小必须配着 MySQL `max_connections` 一起看：

```
worker 数 × (pool_size + max_overflow)  ≤  MySQL max_connections × 0.8
```

生产编排里 app 起 2 个 worker、MySQL `max_connections=200`：
`2 × (10+20) = 60`，留足余量给迁移任务和运维连接。

另外两个必须配的参数：

- `pool_pre_ping=True`：取连接前 ping 一次，避免拿到被服务端单方面掐断的死连接。
- `pool_recycle=1800`：必须小于 MySQL `wait_timeout`（默认 28800s）。
  只配 `pre_ping` 不配 `recycle` 也能活，但会白跑 ping 的往返。

Redis 侧配了 `socket_timeout=0.5s`——**这是熔断能生效的前提**。
没有超时，Redis 挂起时请求会永远等下去，"降级"无从谈起。

### 5.2 uvloop 实测：QPS 没变，P99 变了

两轮 HTTP 压测（真实 uvicorn 进程、真实 TCP、50 并发、每场景 8s、冷缓存起步）：

| 场景 | QPS | P50 | P99 |
|---|---|---|---|
| asyncio + 逻辑过期 | 1278 | 34.3ms | 81.5ms |
| uvloop + 逻辑过期 | 1281 | 35.8ms | **46.1ms** |
| asyncio + 互斥锁 | 1209 | 35.4ms | 95.8ms |
| uvloop + 互斥锁 | 1191 | 38.9ms | **46.1ms** |
| asyncio + 无缓存 | 619 | 64.6ms | 282.2ms |

第二轮复现了同样的形状（asyncio 逻辑过期 P99 89ms，uvloop 54ms）。

**结论要说得准确**：uvloop 在本机 50 并发下**没有提升吞吐**（QPS 差异在噪音内），
但**明显压低了尾延迟**（P99 从 80-95ms 到 46-54ms）。

原因是这个负载的瓶颈不在事件循环：
一次请求的成本主要是"Redis 往返 + 可能的 MySQL 往返"，都是外部 IO 等待，
事件循环只是把它们挂起来。uvloop 优化的是"循环本身做调度/IO 注册的开销"，
所以它改善的是调度抖动（尾延迟），而不是单请求的固有时延（P50 不动）。

**这也说明为什么不能只报 QPS。** 如果只看 QPS，会得出"uvloop 没用"的错误结论；
实际上它对 P99 有稳定改善，而这恰恰是线上更关心的指标。
真要在更高并发下看吞吐差异，需要压到事件循环成为瓶颈才行——那是 Week 5 的事。

### 5.3 压测工具自己成了瓶颈

第一版 HTTP 压测用 httpx，跑出 p50 230ms 的"服务端延迟"。同期：

- `curl` 单请求：0.8–8ms
- 原生 asyncio socket 单请求：3–8ms
- httpx 单请求：**266ms（首次）/ 2.7ms（后续）**

也就是说 httpx 的连接建立开销在这个场景下把结果污染了一个数量级，
所有场景都被压平在 128–160 QPS、P50 230ms 附近，完全看不出差异。

改回原生 asyncio socket 后，数据立刻分层（619 → 1278 QPS）。

**教训**：`压测工具不能成为被测系统的瓶颈`。看到"每个场景都一样慢"时，
第一反应应该是"我的施压端是不是瓶颈了"，而不是"服务就是这样"。

## 6. 降级与熔断

`CircuitBreaker` 的作用范围只有一个：**Redis 操作**。

```
Redis 报错 → trip() → 冷却期 5s 内所有 Redis 操作直接跳过 → 请求走 DB
                    → 冷却期结束放一个请求去探活
```

状态机很简单（closed ↔ open），但有两处值得注意：

1. **所有 Redis 调用都要过熔断检查**，包括读、写、删、埋点。
   漏一处，那条路径就还是"每请求等满 timeout"。
2. **熔断不抛异常、不影响响应**。跳过的语义是"当作未命中"，不是"报错"。

对应测试：`TestDegradation` 四个用例——读失败、写失败、熔断后不再尝试、冷却后恢复。

还有一个**单机多 worker 的现实**：熔断状态是进程内的，2 个 worker 各自独立判断。
这是刻意的取舍——共享熔断状态要么走 Redis（Redis 挂了就没法共享），
要么走额外的协调服务（过度设计）。进程内熔断的语义是
"这个进程已经确认 Redis 不可用"，局部正确就够用。

## 7. API 形态：为什么删除而不是更新

Cache Aside 的写侧约定是"**先更库，再删缓存**"。三个问题要能答：

**为什么删而不是更新缓存？**
- 并发写时"更库 → 更缓存"仍可能被乱序覆盖（两个写请求交错），而删除是幂等的。
- 删完下一次读自然回源，不存在"缓存里是新值、库里是旧值"。
- 更新缓存还要算"新值怎么构造"，可能比读路径更贵（本例里还好，但模式上不该依赖）。

**为什么不先删缓存再更库？**
删完到更库之间有窗口，读请求会把**旧值**重新灌回缓存；而且之后不会再失效——
数据永久脏。这比不删更糟。

**本项目为什么基本用不到删除？**
短链不可变（没有编辑/删除接口），所以 `invalidate()` 目前是个备用的正确性工具，
真正用到它的是"新建时覆盖负缓存"和 Week 6 的话题（如果做"短链过期"，删缓存就会成为主路径）。
**没用到不等于不需要写**——它是"如果我加了修改接口，这里必须这么改"的答案。

## 8. 层级总览

一次 `GET /{code}` 的完整判断顺序，越靠前越便宜：

```
1. 格式校验（is_valid_code）        纯 CPU，非法直接 404
2. 水位守卫                          两个整数比较，或一次 Redis 位图读
3. 缓存读                            一次 Redis GET
4. 负缓存命中                        → 404（第 3 步的一部分）
5. 逻辑过期 / 互斥锁 / 直接回源       一次 MySQL 点查
```

对应代码：`app/api/shortlink.py`（第 1 层） → `app/services/shortlink_service.py`（第 2 层） →
`app/services/cache.py`（3-5 层） → `app/services/prefilter.py`（第 2 层实现）。

`/internal/cache-stats` 暴露这一整套的进程内计数（命中率、回源次数、熔断状态、过滤器拒绝数），
压测脚本读它来核对"这批请求里到底有多少真的查了库"。

## 11. 面试问答预演

**Q: 缓存穿透你怎么解决的？**
A: 两层。前置用"水位守卫"——短码是 Base62(自增 ID)，ID 超过已分配最大值就一定不存在，
O(1) 内存、零假阴性，比布隆过滤器更适合这种单调键空间（布隆要预热、有假阳性、
Redis 清空就得重建）。第二层是负缓存，60s TTL，因为它能挡住过滤器管不了的那类：
号段已分配但号没发出去的"空洞"。实测对"未来号"滤波器把 QPS 从 1.3k 拉到 34k 且零回源；
对"号段内空洞"过滤器完全无效，只能靠负缓存——这两类必须分开测，混在一起会得出错误结论。

**Q: 缓存击穿为什么用逻辑过期而不是互斥锁？**
A: 因为短链不可变。两种我都实现了并压测对比：过期瞬间互斥锁把 P99 从 116ms 降到 82ms、
回源压到 1 次；逻辑过期是 P99 19ms、QPS 6905，因为 99 个请求直接返回旧值、什么都不等。
但逻辑过期在**冷启动**时退化成无保护（没有旧值），这是它的边界。
如果哪天加了"修改目标 URL"的接口，就必须换回互斥锁或引入主动失效。

**Q: 你说的"单飞 bug"是什么？**
A: 压测打出来的。第一版过期瞬间跑出 901 次回源、P99 325ms，比不加保护还差。
两层原因：一是刷新任务拿到锁后没复查，前一个刷完释放锁，排队中的会依次再刷；
二是 100 个请求各 spawn 一个任务、各打一次 SETNX，保护本身成了瓶颈。
修法是"锁内复查 + spawn 前查进程内 inflight 集合"，修完回源 1 次、P99 19ms。

**Q: 缓存雪崩怎么防？**
A: TTL 随机抖动打散过期点，加在写入侧。但要清楚抖动只能挡"集体过期"，
挡不住"Redis 整体挂掉"——那是依赖故障，靠熔断降级：冷却期内跳过 Redis 直接查库，
把故障成本从每请求一次 socket timeout 摊成每冷却期一次探测。
Redis 重启后缓存全空那种情况，多级缓存（本地 LRU）才有意义，Week 5 会测它的实际收益。

**Q: uvloop 有提升吗？**
A: 分指标看。本机 50 并发下 QPS 没有提升（差异在噪音内），但 P99 从 80-95ms 稳定降到 46-54ms，
两轮复现。原因是瓶颈不在事件循环——一次请求主要是 Redis/MySQL 的 IO 等待，
uvloop 优化的是调度开销，所以改善的是尾延迟抖动而不是固有时延。
只看 QPS 会得出"没用"的错误结论。
