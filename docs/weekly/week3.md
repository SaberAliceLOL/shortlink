## 三个真实故障（面试素材）

### 1. 逻辑过期比不加密还慢：单飞写漏了

压测第一版"过期瞬间"：**QPS 2069、P99 325ms、DB 回源 901 次**。
不加任何保护是 4479 QPS / 116ms / 100 次。保护措施让性能**倒退了一半**。

两层原因，压测逐层剥开：

- **刷新任务拿到锁后没复查。** 100 个请求各 spawn 一个刷新任务；第一个刷完释放锁后，
  排队中的任务会依次再拿到锁、各自再查一次库。锁只保证"同时只有一个"，
  不保证"后来者知道前面已经干完了"。
- **单飞做晚了。** 即使复查修好，100 个请求仍各自 spawn 任务、各打一次 `SETNX`。
  保护本身成了瓶颈。

修法：锁内复查 + spawn 前查进程内 `_inflight` 集合。修完 **6905 QPS / P99 19ms / 回源 1 次**。

### 2. 压测构造本身会骗人

修完实现后数据还是不对（回源 901）。这次是测法的问题：我用**一天前**的时钟写入缓存，
让记录一落地就"逻辑过期"。但后台刷新写回的新记录 `expire_at = 一天前 + ttl` **依然是过期的**，
于是每个刷新任务复查后都判定"还要再刷"。

正确做法是回溯 `ttl + 100` 秒。脚本里加了一条断言，确认场景真的处于"存在但过期"才开跑。

**教训**：如果某个优化看起来"完全没效果"，先怀疑测法；但如果实现里真有 bug，
只有正确的构造才能暴露它。这次两个都撞上了。

### 3. 压测工具自己成了瓶颈

第一版 HTTP 压测用 httpx，所有场景都卡在 128–160 QPS、P50 230ms，完全看不出差异。
同期实测：curl 0.8–8ms，原生 asyncio socket 3–8ms，**httpx 首次 266ms / 后续 2.7ms**。

换成原生 asyncio socket 后数据立刻分层（619 → 1278 QPS）。

**教训**：看到"每个场景都一样慢"，第一反应应该是"施压端是不是瓶颈"，而不是"服务就这样"。

## 面试素材（本周新增三个故事）

1. **"为什么不用布隆过滤器"** —— 短码是 Base62(自增 ID)，键空间单调，
   水位守卫零内存、零假阴性、不用预热。布隆的优势（任意键空间）在这里用不上，
   代价却全在。而且过滤器挡不住"号段内空洞"，那只能靠负缓存——两类必须分开测。
2. **"逻辑过期 vs 互斥锁"** —— 两种都实现并压测：过期瞬间 19ms vs 82ms。
   前提是数据不可变；冷启动时逻辑过期退化。能说清"什么时候这个选择会失效"，
   比记住结论更有价值。
3. **"uvloop 到底有没有用"** —— 分指标：QPS 没变、P99 从 82ms 降到 46ms（两轮复现）。
   原因是瓶颈在外部 IO 等待而非事件循环，uvloop 改善的是调度抖动而非固有时延。
   只看 QPS 会得出错误结论。
