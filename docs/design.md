# ShortLink 设计文档（Week 1 · 需求与 API 设计）

> 本文档是 Week 1-2 的施工图，也是"设计决策记录"的正文。
> 每个决策都写成：问题 → 备选 → 选择 → 理由。面试问"为什么"时直接翻这里。

## 1. 需求边界

### 做什么

| 接口 | 语义 | 幂等性 |
|---|---|---|
| `POST /api/shorten` | 长链 → 短码 | 否（同 URL 重复提交生成新码，Week 3 再考虑去重） |
| `GET /{code}` | 短码 → 302 跳转 + 异步计数 | 是（跳转天然幂等，计数允许最终一致） |

**明确不做**（防止业务复杂度吃掉技术深度）：
- 用户系统 / 登录（无 user 概念，全部匿名）
- 自定义短码（与发号器选型冲突，砍掉）
- 编辑 / 删除已生成的短链
- 短链过期（Week 6 做清理任务时再评估）

### 非功能指标（Week 5 压测的靶子）

- 单机目标：读 QPS 3000+（裸 FastAPI + MySQL 基线先测出来再定）
- 读延迟 P99 < 50ms
- 短码长度 ≤ 7 字符（62^7 ≈ 3.5 万亿，远超需求，留足冗余）

## 2. 核心设计决策

### D1：短码怎么生成 —— 号段式发号器 + Base62

**问题**：短码必须全局唯一、短、生成快。

**备选方案对比**：

| 方案 | 长度 | 唯一性 | 生成速度 | 缺点 |
|---|---|---|---|---|
| UUID（截断/全量） | 32+ | 概率唯一 | 快 | 不可读、截断有碰撞风险、无序 |
| 哈希（MD5 取前 N 位） | 可控 | 有碰撞，要处理 | 快 | 碰撞处理逻辑复杂 |
| 数据库自增 ID + Base62 | 6-7 | 严格唯一 | 受限于 DB 写 | 高并发下自增锁是瓶颈 |
| **号段式（本方案）** | 6-7 | 严格唯一 | 快（内存发号） | 实现稍复杂 |

**选择**：号段式（segment mode，美团 Leaf 的简化版）。
App 启动/耗尽时从 MySQL 一次取一段（如 [10000, 20000)），期间发号纯内存自增。
这样 DB 写频率 = QPS / 号段大小，本项目的量级下几乎为 0。

**理由**：
1. 严格唯一且递增 → Base62 后递增，对 InnoDB 聚簇索引是顺序写，不碎页
2. 发号零 DB 交互，Week 5 压测时它不会是瓶颈
3. 能讲清楚"为什么不用 UUID/哈希"——这是短链服务的经典面试题

**Base62 编码**：`0-9 A-Z a-z` 共 62 字符。ID 10000 → `2SG`（3 位），
本服务 ID 起点定为 62^4 = 14,776,336，保证短码 **≥5 位**（不至于短得反直觉）。

**多实例部署的一致性**（Week 2 部署时落实）：号段表 `segment_alloc` 加 `biz_tag`，
不同实例错开号段（step 乘以实例数），或直接步长翻倍。单机部署阶段先不做。

### D2：MySQL 表设计

```sql
CREATE TABLE url_map (
    code      CHAR(7)     NOT NULL COMMENT '短码，主键',
    url       VARCHAR(2048) NOT NULL COMMENT '原始长链',
    created_at DATETIME   NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (code),
    KEY idx_created (created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

要点：
- **主键用 code 而非自增 id**：跳转路径 `WHERE code = ?` 主键点查，一次 B+ 树命中。
  发号器的数字 ID 只在写入侧使用，不落这张表（省一列，也省一次二级索引回表）。
- **url 前缀索引**：如果 Week 3 要做"同 URL 去重"，用 `url_crc` CRC32 列 + 前缀索引，
  不直接给 VARCHAR(2048) 建索引（索引太大）。现在先不做，写入性能优先。

### D3：写入路径（POST /api/shorten）

```
1. Pydantic 校验（必须是 http/https URL，长度 ≤ 2048）
2. 发号器.next_id()          ← 内存自增，号段耗尽才碰 DB
3. Base62(id) → code
4. INSERT url_map            ← 串行写，短链服务写少读多，够用
5. 返回 {code, short_url}
```

### D4：读取路径（GET /{code}）

```
1. code 非法（长度/字符集）→ 直接 404，不碰任何存储   ← 廉价防御
2. Week 1-2（无缓存版）：SELECT url FROM url_map WHERE code = ?
3. Week 3 加：Redis Cache Aside（读穿 + 先更库再删缓存）
4. 302 Location: url   （选 302 不选 301：需要每次都回源统计，且可变更目标）
```

**为什么 302 不 301**：301 是永久重定向，浏览器会缓存，后续请求不再打到服务端——
统计就漏了。302 每次都回源，代价是稍高延迟，换来可统计、可变更。
这是规划 Week 6 "302 vs 301" 的前置伏笔，理由先落在这里。

## 4. 部署形态（Week 2 已落地）

**云服务器 Docker Compose 一键起**：app + MySQL + Redis + Nginx，
公网 IP 直接访问（域名 + 备案 Week 8 前再说）。线上：http://101.200.80.105

### D5：只有 Nginx 暴露公网端口

`ports` 只给 Nginx 的 80，MySQL/Redis/app 全部在 compose 内部网络按服务名寻址。
本地开发用的 `docker-compose.yml` 才映射 3306/6379（开发要连）。

理由：数据库端口暴露公网是最常见的事故来源；两套编排各自只开必需的口子，
而不是靠防火墙"记得关"。

### D6：迁移不进容器启动流程

容器 entrypoint 只启动 uvicorn。`alembic upgrade head` 由 `deploy.sh` 在一次性
容器里显式执行。这样"发布新代码"和"变更 schema"是两个可独立回滚的动作——
如果迁移写在启动脚本里，回滚镜像版本时表结构已经改了，会出现新代码旧表或旧代码新表。

### D7：短码列必须用 `utf8mb4_bin`

**这是 Week 2 真实事故，不只是选型。**

Base62 字符集是 `0-9A-Za-z`，大小写是不同字符。但建表时沿用了库默认的
`utf8mb4_unicode_ci`（大小写不敏感），后果是：

1. 写入：先发 `1012w`、后发 `1012W`，第二条 INSERT 报
   `Duplicate entry '1012W' for key 'PRIMARY'` → 并发下接口 500
2. 读取：`WHERE code = '1012w'` 命中 `1012W` 的记录 →
   **访问者输错大小写会被导向别人的长链**

修法是 `ALTER TABLE url_map MODIFY code ... COLLATE utf8mb4_bin`（迁移 `c4e8d2a6f910`）。
模型侧用 `with_variant(mysql.CHAR(7, collation="utf8mb4_bin"), "mysql")` 而不是直接写
`collation=`：后者会把 MySQL 专有排序规则带进单测的 SQLite，`CREATE TABLE` 直接失败。

**面试可讲的点**：这个 bug 在 SQLite 上无法复现（SQLite 默认就区分大小写），
所以"测试全绿"和"生产正确"之间隔着数据库方言这一层。真正的防线是
应用层测试 + 数据库层迁移双管，缺一不可。

### D8：号段种子数据必须进迁移

`segment_alloc` 只建表不插行时，发号器 `SELECT ... .one()` 抛 `NoResultFound`，
新库上第一次写短链必然 500。本地开发靠手工 INSERT 掩盖了这一点。
迁移 `b7f3a91c2d40` 把初始号段写进去，保证 `upgrade head` 之后的库是可用的。

## 6. 面试问答预演（写代码时同步积累）

- Q: 为什么不用 Redis 自增 INCR 做发号器？
  A: 可用，但 Redis 持久化是异步的，宕机可能回吐已发号段 → 重复码；号段式
     落 MySQL，强一致，且 DB 压力被号段摊薄。
- Q: 短码会冲突吗？
  A: 号段式严格递增，不会。哈希方案才会，需要冲突重试。
- Q: 301 还是 302？
  A: 302，见 D4。可统计性 > 每次几毫秒的额外延迟。

## 7. 号段式发号器的固有代价（W1-D3 实测发现）

进程重启时，本地未用完的号段直接丢弃。实测：首个进程发出 10000（ID=62^4），
重启后第一个号变成 100G8（ID=62^4+1000），中间 999 个号被浪费。

**这是设计上的取舍，不是 bug**：
- 号段跨进程共享需要额外协调（Redis 心跳/租约），复杂度换来的收益（不浪费号）在本项目量级下毫无意义
- 62^7 ≈ 3.5 万亿个号，按每 1000 个号重启一次的极端情况，也够用几百万次重启
- 面试若被问"号段浪费怎么办"：答"加大 step 减少分配频率，或引入双 buffer 预取；
  真正的解法是号段租约（Leaf 的做法），但那是日均亿级请求才需要的优化"

另外两个实测记录：
- `/health` 被兜底路由 `/{code}` 吃掉 → **兜底路由必须最后注册**（FastAPI 按注册顺序匹配）
- 短码格式非法返回 **404 而非 422**：对外部访问者，"短链不存在"比"参数格式错"语义更准确
